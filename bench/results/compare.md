# Sluice vs LiteLLM: added latency and failure behaviour

Generated by `bench/compare.py` (run tag `after`) and `bench/compare_report.py`. Machine: arm64 macOS-26.7.1-arm64-arm-64bit-Mach-O. Sluice on Python 3.14.4, LiteLLM 1.103.1 (Python 3.12). Each gateway is one uvicorn worker on uvloop with access logs off, in front of the same raw-ASGI mock upstream (fixed 50 ms). The load is open loop (`bench/loadgen.py`), measured from each request's scheduled send time, so queueing is not hidden (coordinated omission).

Everything shares one 8-core laptop: generator, mocks and gateway. Absolute numbers are specific to it; the comparison between gateways is the point. Above ~300 rps the generator itself falls behind, so no claims are made there.

Percentiles don't subtract exactly (the p99 request through a gateway isn't the p99 request direct), so read the differences as approximate. Both gateways add the most at the lowest rate; a likely (unverified) cause is CPU frequency scaling on a mostly idle laptop. Reps left out had the load generator itself more than 20 ms behind schedule (a laptop stall); their raw numbers are in the JSON.

## Failover: primary fails 30%, healthy backup, 50 rps (one 20 s run each)

| target | success | p50 | p99 | statuses |
|---|---|---|---|---|
| direct (no gateway) | 69.9% | 54.0 | 58.0 | {'200': 699, '500': 301} |
| sluice | 100.0% | 58.0 | 228.0 | {'200': 1000} |
| litellm | 100.0% | 59.0 | 2809.0 | {'200': 1000} |

Both gateways: retry the primary once, then fall back. Sluice also has a per-provider breaker (3 consecutive failures, 10 s cooldown); LiteLLM has its own cooldowns. Configs are written out in full in `bench/compare.py`.

## Feature comparison (including where Sluice loses)

| | Sluice | LiteLLM | edge |
|---|---|---|---|
| Providers | 1 OpenAI-compatible adapter + mock (Azure/Bedrock not built) | 100+ providers† | LiteLLM |
| Virtual keys | hashed in SQLite, CLI only | Postgres-backed, admin UI† | LiteLLM |
| RPM/TPM limits | token buckets, Redis Lua; verified across 2 replicas here | yes, Redis-backed† | even (Sluice's tested here) |
| Budgets | per key, daily/monthly | per key/team/user† | LiteLLM |
| Retries/fallback | chain + jittered backoff + hand-written breaker | fallbacks, retries, cooldowns | even (both 100% in the failover test) |
| Streaming failure | fail over before first byte only; terminal error event (ADR 0001) | not checked here | - |
| Tracing | OTel GenAI spans per attempt, trace id ↔ cost ledger | many integrations (Langfuse, OTel, Datadog...)† | LiteLLM on breadth |
| Semantic cache | lexical guard; threshold from a labelled eval with false-hit rate | Redis/Qdrant semantic cache† | LiteLLM on maturity; Sluice on measured false hits |
| Quality routing | escalation on free checks; measured: no gain on this workload | not checked here | - |
| Admin UI | none | yes† | LiteLLM |
| Size / maturity | 2,341 lines of Python, one learner, this repo | large project, production users | LiteLLM |

† from LiteLLM's documentation, not exercised in this benchmark. Only latency and the failover scenario above were measured head to head.
