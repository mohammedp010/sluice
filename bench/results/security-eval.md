# Behaviour watch: attacks contained, legitimate traffic disturbed, latency added

Generated by `bench/security_eval.py`: in-process against the real app with the mock upstream ($0), a fake tool server, and a virtual clock driving the shared state.

> **Caveats.** "Seconds" are virtual: they count how long an attack runs at its scripted rate before it is stopped, not network time. The normal day is a traffic model written for this eval (profiles below), not a replay of real traffic, so its false-suspension count shows which everyday noise the rules tolerate, not a rate you can promise. Fake prices make one default request cost $0.40.

## Attacks

| attack | without the watch | with the watch |
|---|---|---|
| A1 stolen key, 10 requests/s from a new network, $50/day budget | 100 requests, **$40.0** before budget_exceeded | 58 requests, **$23.2** in 5.9 s, then suspended (R2_burn_rate); alerts: R3_new_network, R3_new_network, R2_burn_rate |
| A2 guessing tool names, 5/s | every guess answered ("unknown") | 10 guesses in 2.2 s, then suspended (R1 at 10) |
| A3a SQL injection in the bearer (LiteLLM probe shapes) | every attempt answered | IP blocked after **1** request; real key from that IP: 401, from elsewhere: 200 |
| A3b key-shaped guesses, 20/s | every attempt answered | IP blocked after **20** |
| A4 credential in a mail tool's arguments (`mail__*: block`) | forwarded | forwarded with the secret: **0**; key suspended: True; secret in the audit: False |

A1 without the watch is stopped only by the daily budget, as before phase 3. With it, R2 (half the daily budget within 10 minutes) suspends the key; the R3 alert fired on the thief's first request, before any of that.

## A normal day

40 keys, 35,811 chat requests and tool calls over 24 virtual hours:

| profile | keys | requests/day each | budget | tool calls/request | active |
|---|---|---|---|---|---|
| interactive | 24 | 600 | $400 | 0.0 | 08:00-19:00 |
| service | 8 | 1200 | $800 | 0.0 | 00:00-24:00 |
| batch | 4 | 1500 | $1500 | 0.0 | 02:00-03:00 |
| agent | 4 | 400 | $300 | 2.5 | 08:00-19:00 |

Noise in the model: each key uses two office networks plus a laptop on a random network 10% of the time; 1% of agent tool calls use a mistyped tool name; a forgotten deployment retries with a revoked key ~200 times through the day.

- **False suspensions: 0**
- **IP blocks: 0**
- New-network alerts (R3, alert only): 200. Every laptop on a new /24 is one; at this rate R3 is a log, not a pager.

Where false positives come from, by rule (not all of them occur in this model):
- R1: an agent with many refused calls, e.g. a model that keeps inventing a tool name: 10 in 5 minutes suspends it.
- R2: a legitimate job that spends half its daily budget within 10 minutes. The batch profile spends its whole day in an hour, ~1/6 per 10 minutes, and passes; a tighter batch would not.
- R4: many clients behind one NAT or untrusted proxy share an IP, so one stale client retrying 20 times a minute blocks all of them. List the proxy in `auth.trusted_proxies`.

## Latency added

One chat request in-process (mock upstream answers instantly), sequential. Both configurations are warmed up, then measured in alternating rounds (1,800 requests each). The difference is what the key-shape check, IP-block lookup, new-network check, prompt scan and burn-rate counter cost together. Run-to-run noise on this laptop is a few hundredths of a millisecond at p50 and much more at p99.

| state | guards off p50 / p99 | guards on p50 / p99 |
|---|---|---|
| memory | 0.736 / 0.962 ms | 0.762 / 1.154 ms |
| redis | 1.852 / 9.852 ms | 2.281 / 23.542 ms |
